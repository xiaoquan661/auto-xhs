# 经理批量推进复查

日期：2026-09-18。范围：提交 `62a53a4` 与当前经理执行链。

## 结论

本地隔离复现确认批量推进仍需修正，当前提交尚不能作为自动恢复验收依据。

- `manager_agent_service.py` 的周期异常处理将临时规划错误直接写为终态
  `BLOCKED`；下一周期跳过该任务，不能自动恢复。
- `plan.dispatch_failures` 被当作永久跳过列表。账号暂时占用后，故障解除也不会
  再推进该动作；同轮其他动作已接收时周期仍报告 `SUCCESS`。
- `dispatch_task()` 离线时可返回 `success: false / PENDING_DISPATCH`，不抛异常。
  普通运营分支忽略返回值，后续周期遇到已存在任务直接跳过，未继续投递。
- 失败信息通过 `record_operation_plan()` 保存，该方法把运营状态写回 `PLANNING`。
  员工已接收其他动作时，经理仍可能显示规划中。

## 验证

使用 `.venv/Scripts/python.exe`，临时目录内的 `ManagerStore`，复用
`tests/test_manager_agent_service.py` 的 `build_manager`、`create_operation` 和模拟传输；
通过 `unittest.mock.patch` 注入故障。未调用真实员工机或真实账号。

1. 规划阶段抛出一次 `RuntimeError` 后恢复：运营状态 `BLOCKED`，下一轮处理数 0，
   员工接收数 0。
2. 浏览派发抛出 `ServiceError`，评论正常接收：周期 `SUCCESS`、运营 `PLANNING`、
   员工任务 `ACCEPTED`；下一轮浏览动作仍被跳过。
3. 模拟 `accept-task` 暂时离线后恢复：两轮均报告 `SUCCESS`，员工接收数 0，
   员工任务持续为 `PENDING_DISPATCH`。
