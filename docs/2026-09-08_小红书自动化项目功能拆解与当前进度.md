## 一、目标描述

**交付小红书 Mila 经理一套稳定可用的自动化系统：由 1 台经理机通过 SSH 协调 3 台 Windows 执行机，管理 6 个以上小红书账号，并让其他社交平台内容采集与粘贴、内容发现、主动互动、被动互动、发布和数据回收等全部动作至少连续成功运行 3 轮。**

Windows 电脑网页版进一步分成两种角色：

1. **经理机：** 保存执行机清单、任务计划和汇总结果，通过 SSH 向执行机下发固定命令、传输任务文件、收取结果并执行暂停或恢复；经理机不直接操作执行机的 Chrome Profile。
2. **执行机：** 在本机保存账号槽位、Chrome Profile、Bridge、扩展和运行环境，收到经理机任务后在本机完成小红书页面操作并回传结果。
3. **电脑间通信：** 统一使用 SSH；远程命令通过 SSH 执行，任务包、功能包和结果文件通过基于 SSH 的 SFTP 或 SCP 传输。本机 Bridge 的 WebSocket 只负责执行机与本机浏览器扩展通信，不承担跨电脑传输。

当前仓库已有经理机、SSH 调度、执行机注册和跨电脑结果回收代码，已通过自动测试并完成 PC057 部分实机验收；三台执行机的完整联合验收仍待完成。

### 6. 开发环境结论

- **主要开发环境：** Windows 10/11 + Google Chrome 网页版。
- **选择理由：** 当前代码全部围绕 Windows、Chrome Profile、本地 Bridge 和 MV3 扩展构建，复用成本最低，且能够继续扩展为“经理机通过 SSH 调度多台 Windows 执行机”的结构。
- **经理机通信结论：** 电脑之间统一通过 SSH 通信；经理机负责调度和汇总，执行机负责本机账号与浏览器操作，跨电脑不共享或直接读取 Chrome Profile。
- **备用环境：** 无，待用户填写。
- **暂不开发环境：** Android、iOS、电脑手机模拟器和电脑客户端，原因是当前没有相应执行层，均为 `未测试（延期）`。

经理机到执行机的当前主链路为：

```text
经理 Agent 领取运营任务并登记计划
→ SSH 投递任务并唤醒员工 Agent / 执行器
→ 执行机本地 ApplicationService 与账号锁
→ 执行机本地 Bridge
→ 执行机本地 Chrome Profile 与 MV3 扩展
→ 小红书真实网页
→ 页面结果回读和本地记录
→ SFTP/SCP 回传结果文件
→ 经理机汇总任务状态与运营数据
```

## 三、功能拆解

当前主要未完成内容分为以下四个方面。

### 1. 记忆系统、记忆宫殿与记忆回传

- **功能描述：** 建立经理机与员工机共用的运营记忆体系。员工机保存执行过程中的短期记忆，回传经理机整理；适合长期保留的知识进入记忆宫殿，并在后续任务中被检索和使用。
- **输入与前置：** 账号与人设、任务上下文、历史互动、执行结果、异常记录和已有知识；每条记忆具有来源、时间及对应账号或角色。
- **输出结果：** 员工短期记忆、任务交接摘要、记忆回传记录、经理审核结果、记忆宫殿中的长期知识，以及下次执行时采用的记忆引用。
- **业务规则：** 区分共享知识、角色知识、账号记忆和单次任务记忆；事实、推断与建议分别保存。员工经验经过经理整理和审核后进入共享长期记忆。重复回传保持去重，换号后按真实账号区分历史，正在执行的任务保留所用人设与知识版本。
- **验收标准：** 员工完成任务后能保存并回传记忆；经理能看到来源、内容和处理状态；批准的知识可进入记忆宫殿并被后续任务检索；重启、跨日或任务交接后能继续使用相关记忆，且不同账号的数据不混用。
- **当前进度：** **未完成。** 重点补齐记忆结构与存储、记忆宫殿接入、员工记忆回传、经理整理审核、长期知识检索及执行时上下文加载，形成“执行产生记忆 → 回传 → 整理入库 → 下次使用”的完整流程。

### 2. 经理机与员工机完整流程验证

- **功能描述：** 验证经理机从接收运营要求、读取人设与记忆、制定计划到下发任务，以及员工机领取、独立执行、回传结果，再由经理机核对和展示的完整流程；针对验证中发现的问题补齐实现。
- **输入与前置：** 明确的运营任务、目标机器与账号、计划数量、人设、记忆、所需素材及动作授权；经理机和员工机的运行环境可用。
- **输出结果：** 贯穿经理与员工两端的任务记录、领取与执行进度、逐项业务结果、回传与接收状态、经理核对结论，以及问题清单和修复验证记录。
- **业务规则：** 任务下发、员工领取、平台执行、结果回传和经理接收分别记录。同一任务保持可追踪的关联编号；重复下发或回收不重复执行、计数。发布、评论和回复按各自已确认规则执行；结果未知时先核实再决定如何继续。
- **验收标准：** 能从经理端发起一项获准任务，由员工独立完成并回传，经理页面正确显示结果；逐步覆盖浏览、点赞、评论、回复、关注、私信和发布等已纳入范围的能力。中断、离线、恢复及部分失败能准确呈现，并按第四部分运营任务完成多机、多账号和连续轮次验证。
- **当前进度：** **未完成完整验证。** 已有任务投递、员工唤醒和结果回收基础，重点验证各环节实际衔接、员工自主执行、人设与记忆使用、异常恢复和最终业务结果，修复流程中的断点。

### 3. 返回数据全面

- **功能描述：** 补齐员工执行后返回经理机的数据，使经理能够了解任务做了什么、做了多少、对谁执行、具体内容是什么、结果如何，以及账号和运营指标发生了哪些变化。
- **输入与前置：** 原始计划、账号身份、执行过程、平台回读、评论和私信事件、指标快照、异常与记忆记录。
- **输出结果：** 返回任务、机器、账号和时间等关联信息；各动作的目标与实际数量；目标用户或笔记、评论及回复内容、可用位置链接；成功、失败、跳过和结果未知的原因；账号状态、运营指标及变化；记忆回传、数据完整性和采集时间。经理端提供汇总、明细和对应证据。
- **业务规则：** 统计数量以实际执行和平台回读为依据；发布准备、保存草稿与发布成功分别统计。未采集、部分采集和真实零值分别表示；增量注明采样窗口；重复事件和历史修订不重复计数；汇总数据能够追溯到明细。
- **验收标准：** 对照实际执行逐项检查，经理端能完整看到各类动作及结果；评论、回复、关注、私信和发布有对应明细；缺失字段能够说明原因；重复回收和结果修订后统计仍准确；页面、日报与原始回执的口径一致。
- **当前进度：** **未完成。** 已有部分指标和事件返回，重点补齐执行明细、平台结果与链接、入站事件、账号运营信息、指标采集覆盖、异常原因和记忆数据，并贯通员工生成、传输、经理入库与页面展示。

### 4. 回复评论规则和人格

- **功能描述：** 明确评论回复的处理规则，并把账号人格落实到实际回复中。回复应结合笔记正文、原评论、父评论和历史互动，表达符合账号身份、专业领域、语气和语言习惯。
- **输入与前置：** 目标账号、人设与人格设定、相关记忆、笔记和评论上下文、评论处理状态，以及已确认的回复范围、时段和数量规则。
- **输出结果：** 回复、暂缓、跳过或转人工的处理决定，决定依据、最终回复内容、采用的人设与记忆来源，以及发送结果和平台回读。
- **业务规则：** 根据真实内容理解对方意图，避免套用固定话术；信息不足时暂缓或转人工，不编造经历和事实。同一评论保持唯一处理记录；按已确认规则和授权范围发送，超出范围转人工处理。任务使用明确版本的人设，历史互动与长期知识为回复提供依据。
- **验收标准：** 用真实评论检查相关性、自然程度、人格一致性与事实准确性；提问、赞同、质疑及上下文不足等场景有合理处理结果；同账号连续回复保持稳定风格，不同人设有可辨识差异；重复采集不重复回复，发出后有平台回读或明确的结果未知记录。
- **当前进度：** **未完成。** 重点明确回复规则和人格内容，将其接入上下文、记忆检索、回复生成、发送前检查及结果记录，并通过真实评论逐条评估和调整。

## 四、运营任务

运营任务不是软件功能，也不是测试准备；它描述软件投入使用后，在明确期限内需要达到的业务规模或业务结果。

### 1. 运营任务书写规则

每个运营任务固定写清：

1. **任务名称：** 一句话写清要把什么指标做到什么程度；
2. **目标结果：** 写清数量、比例、连续天数或成熟窗口；
3. **当前基线：** 写明开始前的真实数量、比例或最近表现，没有数据时写“待启动前测量”；
4. **完成期限：** 写明截止日期或从前一任务通过后计算的天数；
5. **数据来源与计算口径：** 写明数据来源、去重编号、分子分母以及未成熟和缺采怎样处理；
6. **验收标准：** 列出审核人员可以直接检查的结果和明细证据。

每个运营任务使用稳定编号 `OPS-XHS-xx`，作为同一需求、同一版本和同一负责人下的独立运营进度项，不另建成新需求。

## 六、开发规范

### 1. 版本管理规则

下面以 `PUBLISH-02 执行发布任务` 从1.0升级到1.1为例。

1. **功能编号固定。** 功能实现升级后仍叫 `PUBLISH-02`，只把版本从1.0改为1.1；只有业务目标变了，才建立新的功能编号。
2. **所有可用版本统一登记。** 版本清单分别记录 `PUBLISH-02 1.0｜正式使用` 和 `PUBLISH-02 1.1｜小范围试用`，并写清哪些经理、设备或账号可以使用1.1。
3. **实际执行方选择兼容版本。** 经理 Agent 下发发布任务时给出允许版本范围；真正执行任务的Agent或固定程序根据本机客户端、依赖和版本健康情况，从范围内选择1.0或1.1。
4. **一个任务只使用一个版本。** 某条发布任务开工时选定1.1后，从上传内容到返回结果都保持1.1；结果中必须写明实际版本，执行中不自动切换到1.0。
5. **新版本逐步验证。** 1.1先完成固定测试，再用历史发布任务回放，然后只在一台测试设备和少量测试账号真实试用；通过后才扩大范围。
6. **升级范围可以很小。** 1.1可以先只开放给PC057和指定测试账号，其他发布设备继续使用1.0，不要求所有机器同时升级。
7. **异常只回退后续任务。** 1.1出现问题时，后续新任务切回1.0；已经开工的1.1任务按原任务安全完成或停止，已经形成的平台作品和业务结果不删除。
8. **旧版本最后停用。** 只有1.1验收通过、计划切换范围已完成、并且没有在途任务继续使用1.0时，才能把1.0标记为停用。

一次发布任务至少要留下以下版本记录：

- 功能编号：`PUBLISH-02`
- 允许版本：`1.0至1.1`
- 实际使用版本：`1.1`
- 执行设备：`PC057`
- 执行账号：实际账号编号
- 任务编号：实际发布任务编号
- 选择原因：本机环境通过1.1兼容测试
- 最终结果：成功、失败、待确认或已停止

### 2. 功能包打包规则

下面以 `PUBLISH-02 1.1` 功能包为例。

1. **使用固定目录。** 正式目录为 `../功能包/发布模块/PUBLISH-02/1.1/`；1.0和1.1各自保留独立目录，不能互相覆盖。
2. **一个包只改一个主要功能。** `PUBLISH-02 1.1` 只修改“执行发布任务”；如果同时修改“准备发布预览”，应另建 `PUBLISH-01` 的新版本。
3. **包内先说明身份和入口。** `manifest.json` 必须写明功能编号、版本、适用层级、支持环境、依赖版本、运行入口和执行方式。
4. **执行方式必须明确。** `PUBLISH-02` 标记为 `固定程序执行`；需要Agent分析网络问题的 `DATA-04` 可标记为 `Agent与程序配合`，不能让执行设备靠猜测决定。
5. **交付内容必须完整。** 包内必须同时提供功能说明、正式代码、配置示例、固定测试、历史回放样本、版本变化说明和回退方法。
6. **业务规则放在功能包里。** “不能串账号”“同一任务不能重复发布”等规则属于 `PUBLISH-02`；负责接收、转发和留档任务的公共程序只传递任务和结果，不替发布功能做业务判断。
7. **统一上传且只新增版本。** 开发人员通过局域网上传工具建立1.1目录，记录上传人和时间；禁止覆盖1.0，也不能把桌面或临时目录当作正式交付位置。
8. **先测试，再安装到本机运行。** 1.1通过规定测试后才能列为可用版本；获准设备把功能包装到本机，正式执行时不跨机读取开发人员或经理机器的工作目录，并回报实际安装版本。
