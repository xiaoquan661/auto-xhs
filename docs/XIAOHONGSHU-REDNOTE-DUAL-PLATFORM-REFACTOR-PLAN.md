## 2. 核心结论

项目应采用：

> 一套共享业务和执行主干，加两个独立的平台适配器。

不应复制完整的 `scripts/xhs` 形成另一套长期分叉的 RedNote 实现，也不应为 RedNote 单独维护第二套
WebUI、Bridge 或 Chrome 扩展。

推荐目标结构：

```text
WebUI / CLI / Agent
        ↓
应用服务与任务编排
        ↓
共享业务层
├─ 账号槽位与任务锁
├─ 审批、审计与配额
├─ 统一 Feed / User / Comment 数据模型
├─ 去重、任务状态与结果证据
└─ 发布预览、确认与回读
        ↓
平台路由
├─ XiaohongshuAdapter
└─ RedNoteAdapter
        ↓
Bridge + 通用 MV3 扩展 + 固定 Chrome Profile
        ↓
Xiaohongshu 或 RedNote 网页端
```

第一轮改造优先保证平台隔离、身份正确和只读能力稳定，再逐项开放互动和发布。私信、直播、商业
能力在 RedNote 上保持 `Unknown`，不因页面或接口相似而提前承诺。

## 3. 产品目标与范围

### 3.1 总体目标

使用同一套本地运营控制台，同时管理 Xiaohongshu 与 RedNote 账号，并在不混用账号、Profile、
Cookie、标签页和任务数据的前提下，复用现有核心内容运营能力。

### 3.2 第一轮目标能力

第一轮计划覆盖：

- 创建或导入 Xiaohongshu、RedNote 账号槽位；
- 一个槽位固定绑定一个平台和一个 Chrome Profile；
- Bridge、扩展实例、Profile、平台和登录 UID 联合核验；
- 首页、搜索、笔记详情、评论读取和用户主页；
- 点赞、收藏和评论的逐项适配及结果回读；
- RedNote 图文发布填写；
- 浏览器真实预览、账号与内容确认；
- 用户确认后的发布执行和结果回读；
- WebUI 按平台显示实际可用能力；
- 旧 Xiaohongshu 槽位兼容迁移。

### 3.3 第一轮不承诺的 RedNote 能力

- 私信；
- 直播；
- 商业、交易和广告入口；
- 未经实测的视频和长文发布；
- 受地区、年龄或账号等级限制的能力；
- Xiaohongshu 与 RedNote 所有功能一比一完全对等。

这些能力需要完成登录态盘点和真实账号验证后再单独开放。

### 3.4 平台与 Profile 绑定边界

第一版固定采用：

```text
一个账号槽位 = 一个平台 = 一个固定 Chrome Profile = 一个 Bridge 连接身份
```

不支持一个槽位在两个平台之间动态切换，也不支持一个任务运行过程中改变平台。即使一个 Chrome
Profile 同时登录两个站点，产品层也只把它作为当前槽位所登记的平台使用。

## 4. 当前基线与主要阻断点

现有主干可以继续复用：

- 多账号槽位与 Profile 固定绑定；
- 独立 Bridge 端口；
- 通用扩展配对和实例登记；
- Profile 与扩展连接核验；
- UID 身份保护和半自动换号；
- 同账号任务串行锁；
- 任务、审批、审计和结果记录；
- 内容发现、互动和发布工作流；
- `SUCCESS`、`FAILED`、`BLOCKED`、`CANCELLED`、`RESULT_UNKNOWN` 结果体系。

当前无法直接稳定运行 RedNote 的原因主要是：

1. `AccountConfig` 和身份数据没有 `platform` 字段；
2. 扩展 manifest 只声明 Xiaohongshu 站点权限；
3. 扩展后台、Cookie、标签页选择和网络拦截大量固定判断 `xiaohongshu.com`；
4. Python URL、详情路由、创作平台、通知和私信入口固定为 Xiaohongshu；
5. 登录、发布和部分互动依赖中文文案或国内页面结构；
6. 应用服务和 CLI 直接导入 `xhs` 业务模块；
7. 能力注册表只描述命令风险，没有描述不同平台的能力可用状态；
8. 任务、去重、事件和指标中的内容标识没有平台命名空间。

## 5. 设计原则

### 5.1 共享主干，不复制产品

账号、任务、审批、审计、配额、统一数据模型和结果状态继续共享。只有域名、路由、定位器、登录
身份读取、平台接口和结果回读进入平台适配层。

### 5.2 平台是账号和任务的固有属性

平台不能根据当前浏览器页面临时猜测。账号配置记录目标平台，任务创建时复制平台快照，扩展执行时
再次核对目标平台和当前标签页平台。

### 5.3 平台可用性与操作风险分离

命令风险、确认规则、重试规则继续由统一能力策略管理；某能力是否能在 RedNote 使用，由平台能力
矩阵管理。不能因为风险策略允许执行，就认为平台已经支持。

### 5.4 稳定信号优先于页面文案

页面定位优先使用稳定 DOM 属性、结构、路由和接口结果。中文或英文按钮文案只作为平台专属回退，
不把 RedNote 适配简化为中文字符串翻译。

### 5.5 外部动作必须回读

点赞、收藏、评论、关注和发布不能只以“点击成功”作为成功证据。必须读取页面或平台结果；无法确认
真实结果时返回 `RESULT_UNKNOWN`，不得盲目重试。

### 5.6 旧功能优先保持兼容

双平台改造不能要求现有 Xiaohongshu 用户重建槽位，也不能以牺牲已经工作的 Xiaohongshu 功能为
代价。平台基础设施合入前必须完成现有行为回归。

## 6. 目标架构设计

### 6.1 分层职责

| 层级 | 职责 | 是否平台相关 |
|---|---|---|
| 入口层 | WebUI、CLI、Agent 命令和参数校验 | 仅选择账号，不自行判断网页差异 |
| 应用服务层 | 任务创建、编排、确认、配额、状态转换 | 根据账号平台选择适配器 |
| 共享业务层 | 数据模型、锁、审计、去重、结果证据 | 平台无关，但数据键携带平台 |
| 平台适配层 | URL、路由、定位器、身份、解析、动作和回读 | 平台专属 |
| 浏览器执行层 | Bridge、CDP、通用扩展、Profile 连接 | 共享执行器，执行前核对平台 |
| 平台网页 | Xiaohongshu、RedNote 及各自创作平台 | 外部系统 |

### 6.2 建议模块结构

以下是目标职责划分，不要求一次性移动所有现有文件：

```text
scripts/
├─ platforms/
│  ├─ base
│  ├─ registry
│  ├─ xiaohongshu/
│  │  ├─ spec
│  │  ├─ urls
│  │  ├─ selectors
│  │  ├─ identity
│  │  └─ adapter
│  └─ rednote/
│     ├─ spec
│     ├─ urls
│     ├─ selectors
│     ├─ identity
│     └─ adapter
├─ application_service
├─ capability_registry
├─ platform_capabilities
├─ account_manager
├─ account_identity
└─ business_runner
```

现有 `scripts/xhs` 在迁移期间可以作为 XiaohongshuAdapter 的底层实现。待调用入口全部经过平台路由
后，再决定是否机械移动文件，避免为目录整洁进行高风险的大范围改名。

### 6.3 PlatformSpec

`PlatformSpec` 只保存稳定的静态平台信息：

```text
PlatformSpec
├─ platform_id
├─ display_name
├─ web_origin
├─ creator_origin
├─ supported_hosts
├─ cookie_domains
├─ api_hosts
├─ home_routes
├─ search_routes
├─ detail_routes
├─ profile_routes
├─ notification_routes
├─ locale_defaults
└─ default_capabilities
```

所有 URL 构造和 hostname 识别必须经过平台注册表，业务代码不得继续散落硬编码站点域名。

### 6.4 PlatformAdapter

行为差异由适配器承担，主要契约包括：

| 能力组 | 适配器职责 |
|---|---|
| 导航 | 构造首页、搜索、详情、主页、通知和创作平台 URL |
| 身份 | 判断登录状态，读取 UID、昵称和主页地址 |
| 内容解析 | 将列表、详情、评论和用户数据转换为统一模型 |
| 互动 | 执行点赞、收藏、评论并读取动作后状态 |
| 发布 | 填写素材和正文，进入预览，执行确认后的发布并回读 |
| 诊断 | 识别平台特有的登录、权限、风控和页面异常 |

应用服务只面向统一适配器契约，不直接导入 RedNote 或 Xiaohongshu 的页面实现。

## 7. 账号、身份与任务模型改造

### 7.1 AccountConfig

账号配置增加：

```text
platform: xiaohongshu | rednote
```

旧配置缺少该字段时，读取结果默认为 `xiaohongshu`。迁移前先保持兼容读取，只有进入正式迁移流程时
才写回新版本，避免启动程序时无提示改写真实配置。

### 7.2 身份记录

身份记录统一包含：

```json
{
  "platform": "rednote",
  "user_id": "...",
  "nickname": "...",
  "profile_url": "...",
  "observed_at": "..."
}
```

身份匹配规则：

```text
记录平台 == 当前观察平台
并且
记录 UID == 当前观察 UID
```

平台不一致时返回独立的平台不匹配状态，不把它误报为普通 UID 不一致。

### 7.3 任务平台快照

任务创建时记录：

- `account_slot`；
- `platform`；
- 已核验 UID；
- 创建时的能力状态；
- 目标内容的平台命名空间标识。

执行前再次比较账号当前平台和任务平台。槽位配置在排队期间发生变化时，旧任务应停止，不自动切换到
另一平台继续执行。

### 7.4 内容和去重键

下列键统一使用 `platform + 原始 ID`：

- Feed / Note；
- User；
- Comment；
- Conversation；
- 互动去重；
- 入站事件；
- 运营指标；
- 发布结果记录。

平台字段用于命名空间隔离，不尝试推断两个站点的 UID 或内容 ID 是否全局相同。

## 8. Chrome 扩展与 Bridge 改造

### 8.1 Manifest 权限

通用扩展增加 RedNote 主站和创作平台权限，同时保留 Xiaohongshu 权限。manifest 变更后，所有参与
验收的 Chrome Profile 都需要由用户明确执行一次扩展重载。

### 8.2 平台识别

扩展使用标准化 hostname 与平台注册表识别平台，不使用模糊的字符串包含判断。主站、创作平台和
允许监听的 API 主机分别登记。

### 8.3 Bridge 握手

Bridge/扩展握手增加：

- 当前槽位期望平台；
- 扩展当前标签页观察到的平台；
- 当前 Profile 声明；
- 已登记扩展实例。

账号只有在 Bridge、扩展实例、Profile、平台和 UID 全部符合时才能进入 `READY`。

### 8.4 命令执行边界

每条浏览器命令携带目标平台。扩展在执行前检查：

```text
命令目标平台
= 槽位登记平台
= 当前可操作标签页平台
```

不一致时停止并返回平台不匹配，不自动切换到另一个已打开站点。

### 8.5 Cookie 与网络监听

- Cookie 查询和清理由当前平台的 cookie domain 决定；
- 不跨平台批量清理 Cookie；
- 网络拦截器只处理平台注册的主机；
- 拦截结果统一附带 `platform` 和实际请求 host；
- 诊断逻辑按平台选择需要观察的 API 或异常信号。

## 9. 能力矩阵设计

### 9.1 两类能力信息

继续保留现有全局命令策略：

- 风险等级；
- 是否需要确认；
- 是否允许调度；
- 重试策略；
- 是否需要身份检查；
- 是否需要结果回读。

新增平台能力状态：

| 状态 | 含义 | WebUI 行为 |
|---|---|---|
| `SUPPORTED` | 已完成自动化测试和所需真实验收 | 正常开放 |
| `EXPERIMENTAL` | 已实现但真实证据不足或存在地区差异 | 明确标识后开放给指定验收槽位 |
| `UNKNOWN` | 尚未确认平台是否提供或是否可稳定自动化 | 默认禁用 |
| `UNSUPPORTED` | 已确认当前平台或产品版本不支持 | 隐藏或禁用并说明原因 |

### 9.2 RedNote 初始能力状态

| 能力 | 初始状态 | 转为 `SUPPORTED` 的条件 |
|---|---|---|
| Profile 与 Bridge 连接 | `EXPERIMENTAL` | 平台、Profile 和扩展联合核验通过 |
| 登录状态与 UID | `EXPERIMENTAL` | 登录、退出态和 UID 读取稳定 |
| 首页、搜索、详情、主页 | `EXPERIMENTAL` | 公开与登录态数据解析验收通过 |
| 评论读取 | `EXPERIMENTAL` | 分页和空状态稳定 |
| 点赞、收藏、评论 | `UNKNOWN` | 动作执行和结果回读分别通过 |
| 图文发布 | `EXPERIMENTAL` | 填写、预览、确认、发布和回读闭环通过 |
| 视频、长文发布 | `UNKNOWN` | 单独完成能力盘点和闭环验收 |
| 私信 | `UNKNOWN` | 确认入口、发送机制和会话回读 |
| 直播、商业能力 | `UNKNOWN` | 单独立项验证 |

能力状态可以按平台提供默认值；若地区或账号权限导致差异，WebUI 还应显示该槽位的实际检测结果。

## 10. WebUI 改造范围

### 10.1 账号创建与导入

- 新建或导入槽位时选择平台；
- 平台选择后显示对应主页和创作平台说明；
- 槽位创建完成后不允许无确认地直接改变平台；
- 旧槽位显示为 Xiaohongshu，不要求重新创建。

### 10.2 账号卡片

账号卡至少显示：

```text
平台
固定 Profile
槽位名称
记录账号与 UID
当前登录账号与 UID
Bridge / 扩展 / Profile 状态
平台状态
身份匹配状态
```

### 10.3 任务入口

- 根据所选槽位的平台能力状态更新可选任务；
- `UNKNOWN` 和 `UNSUPPORTED` 能力不能创建可执行任务；
- `EXPERIMENTAL` 能力需要明确展示仍处于验收阶段；
- 搜索结果、任务详情和审计记录显示来源平台；
- 前端不自行拼接平台 URL，由后端提供规范化地址。

### 10.4 发布确认

发布确认页必须同时展示：

- 平台；
- 槽位与固定 Profile；
- 当前核验账号和 UID；
- 发布类型；
- 标题、正文、标签和素材；
- 计划发布时间与可见性；
- 浏览器真实预览状态。

平台、账号、内容或素材任一项发生变化后，原确认失效，需要重新预览和确认。

## 11. 分阶段实施计划

### 阶段 0：RedNote 只读能力盘点

目标：把公开页面和源码推断转化为真实登录态事实。

检查内容：

- 登录后的最终域名和页面语言；
- 当前账号 UID、昵称和主页来源；
- 首页、搜索、详情、评论、主页和通知入口；
- 创作平台入口、草稿入口和账号权限提示；
- 私信、直播、商业入口是否真实存在；
- 地区、年龄或账号状态相关限制。

边界：

- 该阶段需要用户单独授权使用指定 RedNote 槽位；
- 只读取页面，不点赞、不收藏、不评论、不私信、不发布；
- 不更换账号，不清理 Cookie，不修改账号绑定。

阶段产物：

- RedNote 登录态页面和能力事实表；
- 平台 URL、路由、定位器和能力状态更新；
- 无法确认项目清单。

阶段完成条件：能够可靠识别 RedNote 平台、登录状态、当前 UID 和主要只读入口。

### 阶段 1：平台基础设施

改造内容：

- 账号配置增加平台；
- 旧配置兼容读取和迁移；
- PlatformSpec、PlatformAdapter 和平台路由；
- 任务、身份、内容、事件、去重和指标的平台字段；
- 扩展权限、平台识别、Cookie 和网络监听；
- Bridge 握手和命令平台核验；
- WebUI 平台选择、平台徽标和能力过滤。

自动化测试重点：

- 旧账号读取仍默认 Xiaohongshu；
- 两个平台 URL 和 hostname 识别正确；
- 平台不匹配的命令被拒绝；
- 两个平台的数据键不会冲突；
- Xiaohongshu 现有测试没有回归。

阶段完成条件：测试环境中的 Xiaohongshu 和 RedNote 槽位可以独立完成配置、连接、平台和身份状态
流转，现有 Xiaohongshu 功能行为保持不变。

### 阶段 2：RedNote 只读核心能力

推荐顺序：

1. 首页与搜索；
2. 笔记列表和详情；
3. 评论读取；
4. 用户主页；
5. 通知入口只读盘点。

阶段产物：

- RedNote 内容解析适配器；
- 统一 Feed、User、Comment 输出；
- 路由和分页测试夹具；
- WebUI RedNote 只读任务入口和结果展示。

阶段完成条件：相同的应用服务命令可以根据槽位平台选择正确适配器，返回统一数据模型，不包含另一

### 阶段 3：RedNote 互动能力

按以下顺序逐项实现和验收：

1. 点赞；
2. 收藏；
3. 评论。

每项能力必须独立完成：

```text
身份核验
→ 目标预览
→ 执行动作
→ 页面或接口回读
→ 审计记录
```

某一项未通过不会阻止其他已经通过的能力保持开放，但失败能力继续标记为 `UNKNOWN` 或
`EXPERIMENTAL`。

阶段完成条件：真实动作只有在回读状态符合预期时返回成功；无法确认时返回 `RESULT_UNKNOWN`，
且不会自动重复执行。

### 阶段 4：RedNote 图文发布闭环

实施顺序：

1. 打开正确的 RedNote 创作平台；
2. 上传图文素材；
3. 填写标题、正文、标签、可见性和计划时间；
4. 在真实浏览器中进入预览；
5. WebUI 展示平台、账号、内容和素材；
6. 用户确认；
7. 点击发布；
8. 读取发布结果或作品页面；
9. 写入任务终态和证据。

阶段完成条件：未确认不能点击发布；确认后内容发生变化则确认失效；只有获得平台或页面回读才返回
成功，否则返回 `RESULT_UNKNOWN`。

### 阶段 5：高级能力决策

分别评估：

- 视频发布；
- 长文发布；
- 私信；
- 直播；
- 商业和交易入口。

每项能力单独形成调查结论和实施授权，不作为双平台核心改造的阻塞条件。

## 13. 总体验收标准

### 13.1 双平台连接与隔离

- [ ] 一个 Xiaohongshu 槽位和一个 RedNote 槽位可以同时保持连接；

## 14. 结果状态与证据规则

| 结果 | 使用条件 |
|---|---|
| `SUCCESS` | 目标动作完成，并取得平台页面、接口或作品/会话回读 |
| `FAILED` | 已确认动作没有完成，或平台明确返回失败 |
| `BLOCKED` | 登录、权限、平台能力、身份或前置条件阻止执行 |
| `CANCELLED` | 用户取消或确认失效后终止 |
| `RESULT_UNKNOWN` | 已尝试外部动作，但无法确认平台是否已经接受 |

`RESULT_UNKNOWN` 不是失败重试许可。下一步应先读取目标页面或内容状态，确认没有发生后，才能由用户
决定是否重试。

## 15. 数据迁移、发布与回滚

### 15.1 数据迁移原则

- 旧账号缺少平台时按 Xiaohongshu 兼容读取；
- 在自动化测试和迁移预览通过前不批量写回真实账号配置；
- 平台字段加入任务和业务数据时，旧记录按 Xiaohongshu 解释；
- 不推断 RedNote 与 Xiaohongshu 的 UID 或内容 ID 可以互换；
- 迁移错误时保留旧配置，并阻止受影响槽位启动。

### 15.2 发布顺序

推荐发布顺序：

1. 合入平台基础结构，但保持 RedNote 能力关闭；
2. 完成 Xiaohongshu 回归；
3. 为指定 RedNote 验收槽位开启只读实验能力；
4. 只读验收通过后开放 RedNote 只读入口；
5. 点赞、收藏、评论分别验收、分别开放；
6. 图文发布完成完整确认链后再开放；
7. 高级能力继续保持关闭。

### 15.3 回滚方式

- 平台适配失败时可关闭 RedNote 能力，不影响 Xiaohongshu 入口；
- 配置读取保留旧字段兼容，不依赖不可逆的一次性迁移；
- 扩展侧按平台注册表开关 RedNote host 和命令路由；
- WebUI 根据能力状态隐藏 RedNote 尚未开放的任务；
- 外部动作结果不确定时通过回读处理，不以回滚代码代替平台状态确认。

## 16. 主要风险与处理原则

| 风险 | 影响 | 处理原则 |
|---|---|---|
| RedNote 页面或路由更新 | 定位器和导航失效 | 平台适配器集中维护，实施前重新只读核对 |
| 地区和账号权限差异 | 同一能力并非所有账号可用 | 平台默认能力加槽位实际检测结果 |
| UID 是否跨站一致未知 | 身份误匹配 | 始终使用 `platform + UID` |
| 两个平台同时打开 | 扩展选择错误标签页 | 命令、槽位和当前标签页三方平台核对 |
| 英文文案或多语言变化 | 登录和发布定位失效 | 稳定 DOM/API 优先，文案仅回退 |
| 互动接口相似但行为不同 | 错误报告成功 | 每项能力单独实测并强制结果回读 |
| 发布结果提示不同 | 重复发布风险 | 无法确认时 `RESULT_UNKNOWN`，禁止盲目重试 |
| 大范围移动现有 `xhs` 文件 | Xiaohongshu 回归面扩大 | 先建立适配器入口，再渐进迁移 |
