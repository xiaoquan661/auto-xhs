版本：v1.0
状态：开发基线

目标平台：Windows 10/11

## 1. 产品摘要

“自动多账号小红书运营系统”是一套面向个人运营者的本地多账号运营工具。系统以真实
Chrome Profile 承载登录状态，通过通用 Chrome 扩展、Bridge 和 Python 业务能力执行任务，
同时提供三种入口：

- WebUI：面向普通用户的配置、管理、确认、诊断和记录入口；
- Codex/Agent：面向自然语言运营任务的理解与编排入口；
- Python CLI：面向 Agent、自动化调度、测试和高级诊断的标准接口。

三种入口必须共用同一业务服务、安全规则和数据模型。WebUI 不是另一套执行器，Agent 也不是
系统配置的必要条件。

第一版聚焦“跨电脑配置、用户维护热登录和可确认的互动闭环”，支持至少 5 个账号。
用户手动打开每个槽位绑定的 Chrome Profile 并保持小红书页面在线；系统只负责连接、校验和执行，
不自动启动、重启或关闭 Chrome。

## 2. 背景与问题

现有工程已经具备小红书页面操作、多账号槽位、通用扩展安全配对、Bridge 鉴权和登录身份
识别等技术能力，但仍以 CLI 和工程配置为主，普通用户在另一台电脑上使用时会遇到：

1. 不知道本机是否有兼容 Python，也不知道如何安装依赖；
2. 首次添加账号需要打开 PowerShell、进入项目目录并输入多条命令；
3. 创建槽位、选择 Chrome Profile、生成配对包和检查配对状态步骤分散；
4. 用户需要理解 Bridge 端口和进程状态；
5. 关闭命令窗口后，不清楚 Bridge 是否仍在运行；
6. Chrome Profile、扩展连接和登录身份的对应关系尚未完成完整实机验收；
7. 缺少统一任务中心、审计记录、运营报告和可视化故障处理；
8. Agent 承担过多环境配置工作，导致没有 Agent 时系统难以独立使用。

## 3. 产品定位

### 3.1 产品定义

本产品是“基于本地真实 Chrome 的小红书多账号安全运营系统”，不是小红书官方 API 客户端，
也不是让模型临时观察页面并逐步点击的通用浏览器代理。

标准执行链：

```text
用户自然语言或 WebUI 操作
→ 选择预先实现的业务能力
→ 统一权限和账号检查
→ 加载目标账号槽位
→ Bridge 鉴权与路由
→ 通用扩展在目标 Chrome Profile 执行
→ 结果回读与证据保存
→ WebUI/Agent 向用户反馈
```

Codex 的职责是选择和编排已有命令，不是临时生成另一套 Python 自动化程序。

### 3.2 核心价值

- 防止多账号串号、误操作和身份漂移；
- 让不懂代码的用户通过 WebUI 完成配置和日常管理；
- 让 Agent 通过稳定的标准能力完成复杂运营任务；
- 对所有自动化行为提供状态、记录、证据和结果反馈；
- 降低重复运营任务的 Token 消耗和人工操作成本。

## 4. 目标用户

### 4.1 核心用户

同时经营至少 5 个小红书账号的个人运营者，包括品牌矩阵、垂直内容矩阵、客户代运营账号、
测试账号以及不同内容人设账号。

### 4.2 用户能力假设

用户了解基本的小红书运营，但不要求了解：

- Python、虚拟环境或 uv；
- PowerShell 和命令行参数；
- Chrome 扩展开发；
- Bridge、WebSocket、CDP 或端口；
- 服务器部署和进程管理。

## 5. 产品目标与非目标

### 5.1 第一版目标

1. 在 Windows 新设备上通过一键入口完成运行环境检查与系统启动；
2. 用户无需 PowerShell 即可通过 WebUI 完成账号槽位、Profile、扩展和 Bridge 配置；
3. 安全管理至少 5 个账号，标准支持 6 个槽位；
4. 所有账号采用热登录模式，由用户手动打开正确 Chrome Profile 并保持页面开启；
5. 允许浏览、搜索、点赞和收藏，允许 Codex 定时任务自动点赞；
6. 支持评论和回复草稿，并可在 WebUI 编辑；
7. 评论和回复发送前必须展示目标账号、UID、目标对象和最终文本并取得用户确认；
8. WebUI 和 Agent 使用同一套账号配置与安全规则；
9. 在另一台 Windows 电脑上可通过 WebUI 重新配置，再由 Agent 执行定时任务。

### 5.2 第一版非目标

- 不执行图文、视频、长文发布或定时发布；
- 不允许无人值守自动发送评论或回复；
- 不发送私信；
- 不执行公开资料修改；
- 不自动生成或剪辑视频；
- 不建设云端 SaaS、远程控制、多用户组织权限；
- 不复制 Chrome Cookie 或用户 Profile；
- 不绕过验证码、扫码、平台风控或浏览器安全确认；
- 不以自动修改 Chrome Secure Preferences 作为扩展安装方案；
- 不用 WebUI 重写一套与 CLI 分离的业务实现。

发布能力保留兼容代码，但在 V1 的服务层、API 和产品入口统一禁用。评论和回复属于 V1 的
确认后执行能力；私信进入后续版本。
数据采集产品、复杂任务数据库、运营报告和 WebUI 自建调度中心暂缓。

## 6. 核心概念

### 6.1 账号槽位

账号槽位是本地运行容器，不等于小红书账号本身。每个槽位固定关联：

```text
账号别名
+ Chrome User Data / Profile Directory
+ 通用扩展中的独立配对
+ 独立 Bridge 端口和连接凭据
+ 独立任务锁
+ 当前已确认的小红书 UID
+ 用户维护的热登录状态
```

槽位内登录的小红书 UID 可以经过安全换号流程更换，槽位名称和运行资源保持稳定。

### 6.2 通用扩展

所有 Profile 共用一套扩展代码目录；每个 Chrome Profile 通过 `chrome.storage.local` 保存独立
配对。扩展源码可以复用，Profile 内的扩展实例和连接身份不能跨账号复用。

### 6.3 Bridge

Bridge 是只监听本机回环地址的 WebSocket 服务。每个槽位拥有独立且稳定的端口，端口由系统
自动分配和读取，普通用户不需要手工配置。

### 6.4 登录身份

系统必须区分：

- 本地账号槽位；
- Chrome Profile；
- 扩展配对实例；
- 当前小红书登录 UID。

账号进入 READY 前，必须确认这四者的关联符合槽位配置。

## 7. 产品入口与职责

### 7.1 WebUI：配置与管理入口

WebUI 是普通用户的主要入口，负责：

- 首次设置向导；
- 账号和 Profile 配置；
- 通用扩展加载引导和安全配对；
- Bridge、Chrome 和登录状态管理；
- 热登录连接检查、人工恢复提示和安全配置；
- 权限、限速和风控规则；
- 草稿编辑、发送确认、最小执行结果、诊断；
- 版本和本地更新状态。

没有 Agent 时，用户也必须能够通过 WebUI 完成全部配置管理。

### 7.2 Codex/Agent：运营任务入口

Agent 负责：

- 理解自然语言运营目标；
- 从已注册能力中选择命令；
- 拆解复合任务；
- 明确目标账号；
- 根据固定权限元数据处理确认；
- 读取执行结果并反馈。

Agent 默认读取已有配置，不应在用户未要求时自动创建槽位、更换 Profile、撤销配对、启用
自启动或修改限速规则。

### 7.3 Python CLI：标准执行接口

CLI 面向 Agent、测试、自动化调度和高级诊断。CLI 与 WebUI 必须调用同一个 Python 业务服务层，
不能通过复制逻辑或在 WebUI 中拼接任意 Shell 字符串实现功能。

## 8. 总体架构

```text
Codex / Agent ──→ CLI Adapter ─┐
                               ├→ Application Service Layer
Local WebUI ──→ Local API ─────┘          │
                                           ├→ Account / Profile Manager
                                           ├→ Task / Approval / Audit
                                           ├→ Bridge Lifecycle Manager
                                           └→ XHS Business Adapters
                                                      │
                                            Local WebSocket Bridge
                                                      │
                                            Universal Chrome Extension
                                                      │
                                            Target Chrome Profile / XHS
```

本地 API 和 WebUI 只监听 `127.0.0.1`。所有高风险规则必须在服务层强制执行，不能只依赖 WebUI
按钮是否显示或 Skill 提示词。

## 9. 新设备安装与启动

### 9.1 一键启动要求

第一版必须提供 Windows 一键启动器或桌面快捷方式，用户不需要打开 PowerShell。启动器负责：

1. 检测项目虚拟环境；
2. 检测本机兼容 Python 3.11+；
3. 检测项目依赖；
4. 启动本地 Web 服务；
5. 打开默认浏览器进入 WebUI；
6. 防止重复启动多个控制台服务。

### 9.2 Python 与 uv 策略

环境选择顺序：

1. 显式配置的项目 Python；
2. 项目 `.venv`；
3. 本机兼容 Python；
4. 均不存在时，使用 uv 准备托管 Python。

uv 仅作为缺少兼容 Python 时的运行时和依赖管理兜底，不替换文档中的全部 CLI 命令。下载和
安装软件属于 L3 操作，必须展示来源、用途和影响并取得用户明确同意。

### 9.3 安装入口

系统支持两条安装路径：

- Agent 安装：Agent 下载项目并运行引导器，完成后打开 WebUI；
- 用户安装：用户运行安装包或一键启动器，由图形界面完成环境引导。

两条路径完成后进入同一个 WebUI 首次设置向导。

## 10. WebUI 信息架构

第一版至少包含以下页面：

1. 首次设置向导；
2. 账号总览；
3. 账号详情与添加账号向导；
4. 草稿与确认中心；
5. 最小执行结果；
6. 系统设置；
7. 诊断与版本信息。

V1 不在 WebUI 内自建定时调度中心，定时任务暂由 Codex 自带任务功能承担。

## 11. 首次设置向导

目标流程：

```text
欢迎页
→ 检查运行环境和 Chrome
→ 创建第一个账号槽位
→ 新建或选择 Chrome Profile
→ 提示用户手动打开目标 Profile
→ 检查/引导加载通用扩展
→ 发起一次性安全配对
→ 用户在扩展中确认
→ 检查小红书登录
→ 用户扫码或验证
→ 读取并确认 UID
→ 确认热登录常驻要求
→ 完成配置
```

每一步必须显示当前状态、系统自动完成的内容、用户需要完成的内容、失败原因和重新检测入口。

## 12. 账号与 Profile 管理

### 12.1 添加账号

用户在 WebUI 中输入槽位名称并选择：

- 新建独立 Chrome Profile；
- 绑定本机已有 Chrome Profile。

系统自动完成槽位创建、端口分配、配置保存和配对准备。Chrome Profile 由用户手动创建或打开，
系统不得代为启动、重启或关闭。

### 12.2 Profile 数据保护

- 不复制现有 Chrome Profile；
- 不导出 Cookie；
- 一个 Profile 默认只能绑定一个槽位；
- 重新绑定必须明确展示旧关系并要求 L3 确认；
- 删除槽位默认保留 Chrome Profile 和浏览器数据；
- 配置写入必须原子化，失败时回滚不完整资源。

### 12.3 热登录 Profile 连接

系统保存槽位绑定的 `user-data-dir` 和 `profile-directory`，用于识别用户已经手动打开的
Chrome Profile。系统不得根据这些路径自动启动 Chrome，也不得接管或关闭用户窗口。

检测到扩展连接后，仍必须校验扩展实例、槽位配对和小红书 UID；仅 Bridge 在线不能进入 READY。

## 13. 通用扩展安全配对

### 13.1 配对流程

```text
WebUI 创建或恢复槽位
→ 启动 Bridge，并提示用户手动打开目标 Chrome Profile
→ 创建短时、单次使用的配对请求
→ WebUI 显示等待确认
→ 用户在目标 Profile 的扩展弹窗中核对并确认
→ Bridge 登记扩展实例并轮换长期连接凭据
→ WebUI 自动检查 paired/connected
```

配对包可以自动传递到剪贴板或扩展，但浏览器中的最终确认不能被 Agent 或 WebUI 绕过。

### 13.2 安全要求

- 默认 5 分钟过期；
- 只能消费一次；
- 服务端只保存配对密钥摘要；
- 不进入日志、报告或任务内容；
- 不能跨槽位、跨 Profile 复用；
- 撤销配对后必须轮换长期凭据；
- 共享扩展代码目录不得包含真实账号名、端口或长期令牌。

## 14. Bridge 与热登录 Chrome 生命周期

### 14.1 Bridge 管理

- 每槽位端口独立且稳定；
- 只监听回环地址；
- CLI、Bridge 和扩展三方校验账号连接身份；
- Bridge 启动后应脱离临时 PowerShell 或 Agent 父会话；
- WebUI 提供启动、停止、重启、状态和诊断；
- 进程管理必须记录并验证 PID，不能误杀其他端口进程；
- 异常退出应按有限重试策略恢复，连续失败后熔断。

### 14.2 热登录运行模式

所有账号由用户手动打开槽位绑定的 Chrome Profile，并保持小红书页面和通用扩展在线。任务到来
时，系统只启动或恢复 Bridge，然后核验扩展上报的 Profile、已登记扩展实例和登录 UID。系统不
启动 Chrome、不关闭 Chrome，也不清理或重置浏览器会话。

运行状态必须区分：

- Bridge 在线；
- Chrome 在线；
- 扩展已连接；
- 小红书已登录；
- UID 已验证；
- READY。

不能因为 Bridge 已监听端口就把账号标记为 READY。

### 14.3 当前验证状态

- Bridge 脱离父进程：代码与自动化测试已覆盖；
- Windows 登录自启动：只允许恢复 Bridge，代码已实现，待真实计划任务验收；
- 自动打开指定 Chrome Profile：已从 V1 删除；
- 热登录 Profile、扩展和 UID 对应关系：待真实设备验收；
- 浏览器未连接时任务进入 BLOCKED，不尝试自动恢复 Chrome。

## 15. 账号状态机

```text
UNCONFIGURED
→ SLOT_CREATED
→ PROFILE_CONFIGURED
→ HOT_SESSION_REQUIRED
→ EXTENSION_REQUIRED
→ PAIRING_REQUIRED
→ PAIRED
→ LOGIN_REQUIRED
→ IDENTITY_REQUIRED
→ READY
```

运行中可能进入：

```text
OFFLINE
DEGRADED
IDENTITY_MISMATCH
RISK_BLOCKED
SWITCHING_ACCOUNT
ERROR
```

WebUI 必须根据状态提供唯一、明确的下一步操作，不能只显示笼统的“失败”。

## 16. 登录身份与安全换号

- 扩展配对与小红书登录是两套独立状态；
- 登录、验证码、退出和换号属于 L3；
- 登录完成后读取 UID、昵称和规范主页地址；
- 用户确认后把 UID 记录为槽位身份基准；
- 高影响业务操作前重新验证当前 UID；
- UID 不一致时停止业务任务，不自动猜测或切换账号；
- 换号必须经过开始、登录、完成或取消状态机；
- 换号过程暂停该槽位的普通运营任务并保留审计记录。

## 17. 四级操作权限模型

| 等级 | 类型 | 第一版示例 | 执行规则 |
|---|---|---|---|
| L0 | 只读观察 | 浏览、搜索、详情、主页、采集、状态检查 | 明确账号后可自动执行和有限重试 |
| L1 | 非内容输出型状态操作 | 点赞、取消点赞、收藏、取消收藏、滚动 | 可自动执行，但必须限速、去重和审计 |
| L2 | 内容输出与对外沟通 | 发布、评论、回复、私信、公开资料修改 | V1 仅开放评论和回复，必须基于 WebUI 最终草稿即时确认；发布、私信和资料修改不开放 |
| L3 | 身份、安全和系统配置 | 安装、登录、验证码、换号、配对、删除、启用自启动 | 必须显式确认，不得批量静默授权 |

每个命令必须登记固定元数据：

```text
command
risk_level
requires_confirmation
supports_scheduling
supports_auto_retry
requires_target_account
requires_identity_check
requires_result_verification
evidence_level
```

Agent 和 WebUI 只能读取该元数据，不能自行降低权限等级。

## 18. 任务模型与工作流

标准任务流程：

```text
用户提出运营目标
→ 系统拆解任务
→ 展示执行计划
→ 按风险等级处理确认
→ 调度执行
→ 验证结果
→ 保存证据
→ 反馈结果
```

每个任务必须包含：

- 用户原始目标；
- 明确的账号槽位；
- 预期结果和完成标准；
- 子步骤和依赖关系；
- 各步骤风险等级；
- 确认或预授权状态；
- 调度时间和重试规则；
- 执行结果、错误和证据。

第一版核心闭环：

```text
WebUI 配置账号和 Profile
→ 用户保持热登录，系统核验连接和身份
→ 浏览/搜索/点赞/收藏
→ 评论、回复草稿
→ WebUI 编辑并确认发送
→ 返回最小执行结果
```

## 19. 调度与并发

- 不同账号的独立 L0/L1 任务可以并发；
- 同一账号的页面操作必须串行；
- 第一版全局最多 3 个业务任务并行，同一账号必须串行；
- 全局并发上限和每账号配额可在 WebUI 配置；
- L1 必须有单任务、每小时和每日数量限制；
- 操作间隔加入合理随机性，但不得用于绕过平台规则；
- 连续失败、验证码、异常登录或风控信号触发熔断；
- 任务支持等待、运行、成功、失败、阻塞、取消和结果未知状态。

WebUI 自建任务队列和完整状态机暂缓。Codex 自带任务负责触发；执行层仍必须返回成功、失败、
阻塞或结果未知，且 `RESULT_UNKNOWN` 禁止直接重试外部状态操作。

未来任务状态机：

```text
DRAFT → READY → QUEUED → RUNNING
                         ├→ SUCCESS
                         ├→ FAILED
                         ├→ BLOCKED
                         ├→ CANCELLED
                         └→ RESULT_UNKNOWN
```

`RESULT_UNKNOWN` 禁止直接重试外部状态操作，必须先回读平台状态。

## 20. WebUI 页面需求

### 20.1 账号总览

展示账号别名、UID/昵称、Chrome、Bridge、扩展、登录、READY、当前任务和最后活动时间。提供
检查、登录、重新配对和账号设置入口；Chrome 离线时提示用户手动打开对应 Profile。

### 20.2 添加账号向导

完成槽位、Profile、扩展、配对、登录和身份确认，并明确提示热登录常驻要求。用户不需要看到
Python 路径或 CLI 参数，Chrome 由用户手动打开。

### 20.3 草稿与确认中心

编辑评论和回复草稿。发送确认必须包含目标账号、当前 UID、目标对象、最终文本、影响、
有效期和确认来源；草稿修改后旧确认自动失效。

### 20.4 最小执行结果

按任务、账号、命令、状态和时间查询。能够查看步骤时间线、错误分类和脱敏证据。

复杂执行记录、数据分析和日报/周报在 V1 暂缓，只保留安全排错需要的最小结果。

### 20.5 系统设置与诊断

管理 Bridge 自启动、并发、配额、熔断、版本和更新；检查运行环境、Profile、Bridge、扩展、登录
身份并导出脱敏诊断报告。Bridge 自启动不得连带启动 Chrome。

### 20.6 全局暂停

提供“暂停全部自动化”按钮。暂停不删除账号、任务、确认和审计数据；正在进行的不可安全中断步骤
应完成当前原子步骤后停止。

## 21. 审计、证据与反馈

### 21.1 任务记录

至少包含：

```text
task_id
用户原始指令
目标账号槽位
任务类型
创建/计划时间
风险等级
确认状态
最终状态
结果摘要
```

### 21.2 操作事件

至少包含：

```text
event_id
task_id
account_slot
已验证 UID
能力/CLI 子命令
开始与结束时间
操作对象
执行结果
错误类型
重试次数
Bridge/扩展状态
页面 URL
证据引用
```

### 21.3 禁止记录

不得保存或展示：

- Cookie、密码和 Chrome 加密凭据；
- 手机验证码；
- Bridge 长期令牌；
- 一次性配对包；
- GitHub Token；
- 未脱敏手机号；
- 用户未授权保存的私密内容。

### 21.4 结果反馈

每个任务必须得到成功、失败、阻塞或结果未知反馈，包含账号、目标、数量、耗时、风控状态、结果
位置和建议下一步。被权限或身份检查阻止的操作也必须记录原因。

## 22. 数据与存储

第一版所有账号配置、连接凭据、最小确认和执行结果保存在本机，不上传云端。

建议分层：

- 账号配置与非公开连接凭据：受限本地配置目录；
- 复杂任务、事件、报告和 SQLite 迁移体系：本版暂缓；
- 截图及其他大证据：本地文件目录，数据库保存引用；
- WebUI 静态资源：项目或打包资源目录。

账号配置继续使用 `schema_version` 和显式迁移。敏感文件必须限制本机访问权限，状态接口默认
脱敏。跨电脑迁移只迁移程序和非秘密配置结构；目标电脑的 Profile 与扩展必须重新选择和配对。

## 23. 安全与隐私要求

- Web 服务、API 和 Bridge 默认只监听 `127.0.0.1`；
- WebUI 修改状态的请求需要本地会话保护和 CSRF 防护；
- 普通 CLI 请求必须验证槽位连接身份；
- 所有 L3 操作需要显式、可审计确认；
- WebUI 不能通过隐藏按钮代替服务端权限校验；
- 账号别名、路径和 Profile Directory 必须防止路径穿越；
- 端口分配、账号创建和配置写入必须受全局事务锁保护；
- 删除操作默认保留 Profile，并明确列出将删除的数据；
- 更新前检查本地未提交改动和版本兼容性，不能静默覆盖用户配置。

## 24. 可靠性与可维护性

- 关键配置采用临时文件加原子替换；
- Bridge 和 WebUI 进程有 PID、身份和健康检查；
- 页面业务适配器使用多候选定位、前置状态检查和结果回读；
- 小红书页面无法识别时停止写状态操作，不盲点；
- 页面适配器具有版本和回归用例；
- L1 操作使用幂等键或对象去重；
- 自动重试有次数、退避和错误分类；
- 测试至少覆盖服务层、API、CLI、配对协议、双账号隔离和真实 Chrome 验收脚本；
- CLI JSON 与 Web API 使用稳定错误码和一致状态语义。

## 25. 易用性要求

- 普通流程不要求 PowerShell；
- 默认隐藏端口、令牌、Python 路径和内部命令；
- 每个异常状态提供人类可读原因和一个推荐动作；
- 账号相关确认始终显示账号别名和已验证昵称/UID；
- 危险操作不能只询问“是否继续”；
- WebUI 在 1366×768 分辨率下可完成核心配置；
- 首次设置支持中断后继续，不重复创建槽位或配对请求；
- UI 文案使用中文，技术详情放入可展开的高级区域。

## 26. 第一版验收标准

### 26.1 安装与启动

- 新 Windows 设备可通过一键入口启动系统；
- 有兼容 Python 时不强制安装 uv 或另一套 Python；
- 无 Python 时展示说明并在确认后完成托管运行时准备；
- 用户无需打开 PowerShell 即可进入 WebUI；
- WebUI 和本地 API 不可从非本机地址访问。

### 26.2 账号配置

- 用户可完全通过 WebUI 创建新槽位或绑定已有 Profile；
- 6 个槽位的端口和运行身份互不冲突；
- 通用扩展目录只维护一份；
- 每个 Profile 的配对实例独立；
- 配对包过期、复用和跨账号使用均被拒绝；
- 配对、登录和 UID 核验后才进入 READY。

### 26.3 热登录 Profile 端到端验收

对两个测试槽位分别验证：

1. 用户手动打开的是配置指定的 Profile；
2. 两个槽位不会绑定或连接同一个 Profile；
3. Profile 原有小红书登录状态正确保留；
4. 扩展读取对应 Profile 自己的配对；
5. 扩展自动连接正确 Bridge；
6. 当前 UID 与槽位身份基准一致；
7. 用户关闭 Profile 后任务进入 BLOCKED，重新手动打开后能够恢复正确关系；
8. 全流程系统不会自动启动、重启或关闭 Chrome。

### 26.4 运行与任务

- 所有账号采用热登录，任务到来时只使用用户已打开的槽位指定 Profile；
- 关闭启动命令窗口后 Bridge 仍可运行；
- Profile 声明或已登记扩展实例与槽位配置不一致时拒绝进入 READY；
- 同账号任务串行，不同账号在全局上限内并发；
- L0 自动执行，L1 受配额、去重、风控和审计控制；
- 评论和回复只能在用户确认 WebUI 最终草稿后执行；其他 L2 拒绝执行；
- L3 未确认时拒绝执行；
- 每个任务都有最终状态、事件记录和用户反馈。

### 26.5 WebUI

- 用户无需 Agent 即可完成账号、Profile、扩展、Bridge 和安全设置；
- Agent 能读取 WebUI 已配置的账号并执行允许的任务；
- CLI 与 WebUI 对相同操作返回一致状态；
- 全局暂停能够阻止新任务进入执行；
- 可查看账号状态、草稿、确认、最小执行结果和诊断。

### 26.6 跨电脑最终验收

在另一台 Windows 电脑上完成：启动 WebUI、用户自主添加账号、选择正确 Profile、加载并配对
扩展、核验 UID，并保持对应 Chrome 页面开启，再由 Agent/Codex 定时任务完成一次自动点赞。
全流程普通用户不需要打开 PowerShell；如果浏览器未连接，任务应明确进入 BLOCKED。

## 28. 开发阶段

## 29. 需求追踪规则

开发过程中每项需求使用以下状态：

```text
PLANNED
IN_PROGRESS
IMPLEMENTED
AUTOMATED_TESTED
REAL_DEVICE_VERIFIED
BLOCKED
DEFERRED
```

“代码存在”只能标记为 IMPLEMENTED；必须通过自动化测试后才能标记 AUTOMATED_TESTED；涉及
Chrome、Profile、扩展、登录和 Windows 启动的能力必须完成真实设备验证后才能标记
REAL_DEVICE_VERIFIED。

每个开发阶段结束时必须更新追踪矩阵、测试结果、已知限制和用户可见文档，再进入下一阶段。

## 30. 发布门槛

第一版可以对普通用户发布前，必须满足：

1. 阶段 1—5 的 P0 项全部完成；
2. 所有自动化测试通过；
3. 两台 Windows 设备完成全新安装验收；
4. 至少两个真实 Chrome Profile 完成防串号端到端验收；
5. 热登录账号持续连接、离线 BLOCKED 和人工恢复完成持续运行验证；
6. 评论和回复必须确认后执行，其他 L2 在 UI、API 和产品 CLI 默认禁用；
7. 不记录或泄露 Cookie、验证码、长期令牌和配对包；
8. 用户可以不打开 PowerShell、不依赖 Agent 完成系统配置；
9. 所有执行都有明确最终结果，确认和安全排错信息可查询；
10. 已知限制、恢复方法和卸载保留数据策略形成文档。

### 30.1 产品成功指标

- 新用户在真实设备上 15 分钟内让第一个账号进入 READY；
