## 一、目标描述

交付一套由经理机统一管理员工机、账号、人设、运营任务、结果和异常，员工机负责本机账号、任务执行、结果回传与现场处理的双角色运营网站。

## 三、功能拆解

### 1. 功能书写规则

每个功能写清：功能描述、输入与前置、输出结果、业务规则、验收标准和当前进度。当前进度分别记录代码、自动测试和实机验证，不互相替代。

### 2. 经理机网站

#### MANAGER-FRONT-01 顶部导航与运营总览

- **功能描述：** 在页面顶部提供运营总览、运营任务、员工机、账号与人设、数据回收、异常中心和系统设置七个入口；首页汇总集群、任务、目标、异常和同步时间。
- **输入与前置：** Manager Console 静态资源和经理机统一快照可访问。
- **输出结果：** 顶部导航、集群指标、当前运营任务、员工机摘要、异常摘要和最近同步时间。
- **业务规则：** 全局导航不写死员工机编号；页面读取经理机缓存；缓存过期时显示更新时间和 `UNKNOWN`。
- **验收标准：** 页面切换不整页刷新；自动刷新不重置当前视图；1440px 首屏能够看到核心指标。
- **当前进度：** `已验证`。2026-09-07 完成七入口切换、刷新保持、1440px 首屏、过期缓存及执行任务统计验收，功能包为 1.0。

#### MANAGER-FRONT-02 运营任务与 Agent 协作

- **功能描述：** 创建业务级运营任务，展示任务列表、目标、计划、员工机执行、Agent 协作时间线、结果和审计信息。
- **输入与前置：** 目标机器、账号、指标、执行说明、人设和操作授权范围明确。
- **输出结果：** `WAITING_AGENT` 任务，以及领取、规划、派发、ACK、进度、结果、回收和完成事件。
- **业务规则：** 用户不填写 SSH 或 CLI 原子命令；Manager Agent 负责领取、规划和派发；技术 payload 默认折叠。
- **验收标准：** 可按状态、机器、账号、日期和关键词筛选；任务详情可以追踪完整协作链和目标/实际。
- **当前进度：** `已验证`。2026-09-07 完成 PC057 浏览任务的领取至回收完成全链验收，逐篇进度在执行期间经 outbox 回收；筛选和详情通过页面验证。评论阶段事件通过自动测试，实机覆盖范围为浏览任务。功能包为 1.0。

#### MANAGER-FRONT-03 员工机管理

- **功能描述：** 根据动态拓扑展示全部员工机，并在同一页面切换单机详情。
- **输入与前置：** 员工机已登记或已回传机器数据。
- **输出结果：** 机器状态、SSH、执行器、账号槽位、当前任务、最近 ACK、回收时间和异常。
- **业务规则：** 前端不写死 `PC057`；离线机器继续显示最后缓存；所有操作明确目标机器。
- **验收标准：** 新机器登记后自动出现；机器详情按身份、连接、任务、协作、结果、回收和异常展示。
- **当前进度：** `部分实机验证`。2026-09-07 完成 PC057 单机详情实测，以及四节点模拟拓扑、新增节点自动出现、离线缓存和选择保持验收；多员工机实机验收待完成。功能包为 1.0。

#### MANAGER-FRONT-04 账号与人设统一管理

- **功能描述：** 经理机集中查看所有员工机账号，维护账号备注、调度状态和长期人设，并发起远程账号操作。
- **输入与前置：** 员工机已回传账号清单；操作包含明确的机器编号和账号槽位。
- **输出结果：** 昵称、UID、登录、Bridge、扩展、Profile、状态、人设、当前任务、数据来源和更新时间。
- **业务规则：** 经理机配置不得覆盖员工机真实回执；扫码和验证码在账号所在员工机完成；已开始任务保留人设快照。
- **验收标准：** 支持按机器、状态、人设和任务筛选；可发起检查、诊断、Bridge 重启、Profile 启动和现场处理请求。
- **当前进度：** `已实现`。远程账号缓存、账号操作、现场请求、人设编辑和绑定已有自动测试。

#### MANAGER-FRONT-05 数据回收与结果审计

- **功能描述：** 分开展示当前有效结果、逐项/增量数据和历史修订。
- **输入与前置：** 员工机已产生结构化结果，或经理机已有历史缓存。
- **输出结果：** 目标/实际、终态、评论文本、浏览明细、产生时间、回收时间、完整性和修订历史。
- **业务规则：** 同一远程执行只以最高修订版本计入当前结果；旧修订只进入审计；缺失数据不解释为 0。
- **验收标准：** `RESULT_UNKNOWN` 和后续修订均可追溯；重复回收不重复计数；逐项结果可从任务详情查看。
- **当前进度：** `已实现`。当前结果、增量数据、修订去重和 `RESULT_ACK` 已有自动测试及 PC057 在线回收证据。

#### MANAGER-FRONT-06 异常中心与系统设置

- **功能描述：** 集中展示机器、账号、任务、结果和回收异常，并管理运行参数、SSH、模型、功能包、版本和诊断。
- **输入与前置：** 经理机快照、同步状态和设置服务可读取。
- **输出结果：** 待处理异常、影响对象、建议动作，以及设置、传输、版本和诊断结果。
- **业务规则：** 高影响操作必须明确机器和账号；传输失败不得显示为已安装；已解决异常不继续计入当前待处理量。
- **验收标准：** 离线、身份异常、任务失败、结果未知和回收异常可以区分；设置结果能够回读。
- **当前进度：** `部分实现`。异常聚合和设置页已实现；异常处理中、已解决分组及处置记录待补齐。

### 3. 员工机网站

#### WORKER-FRONT-01 执行概览与当前任务

- **功能描述：** 展示本机执行器、经理机连接、账号、当前任务、ACK、执行阶段、目标/实际和最近动作。
- **输入与前置：** `/api/v1/worker/snapshot` 可访问，员工机已经接收任务时包含执行状态。
- **输出结果：** 机器状态、账号身份、inbox/outbox、当前阶段、浏览/点赞/评论进度和评论文本。
- **业务规则：** 只展示本机数据；不得修改运营目标、计划或人设快照；结果未知时不提供直接重跑按钮。
- **验收标准：** 收到任务后及时显示 ACK；执行期间逐项更新；完成后显示真实终态。
- **当前进度：** `部分实现`。页面和进度渲染已通过自动测试，执行期间的逐项实时刷新待实机验收。

#### WORKER-FRONT-02 执行记录、回传队列与本机操作

- **功能描述：** 查看本机历史任务和 outbox 状态，并执行暂停、恢复、重启、刷新、诊断及现场账号请求。
- **输入与前置：** 本机执行记录、结果目录和本地会话可用。
- **输出结果：** 历史任务、逐项结果、待回传/已回传数量、高水位、错误、本机操作反馈和现场处理结果。
- **业务规则：** 不展示其他员工机；历史查看不触发再次执行；本机操作不影响其他机器。
- **验收标准：** 支持账号、状态、能力和日期筛选；结果写入与经理机回收后队列状态正确变化。
- **当前进度：** `已实现`。页面、接口和本地会话保护已有自动测试，PC057 已完成一次真实结果回收。

### 4. 数据与交互

#### DATA-FRONT-01 统一快照、缓存与状态

- **功能描述：** 经理机后端聚合机器、账号、人设、任务、Agent 消息、结果、异常和数据新鲜度后统一返回页面。
- **输入与前置：** 经理机状态库和各同步周期已有可读取数据。
- **输出结果：** 统一页面快照，以及 `READY`、`WARNING`、`BLOCKED`、`UNKNOWN` 等标准状态。
- **业务规则：** 前端不直接读取远程文件，不跨来源推断终态；员工机离线不删除最后缓存。
- **验收标准：** SSH 断开时页面仍可读取；管理数据与员工机回执来源明确；状态用词一致。
- **当前进度：** `已实现`。统一快照、账号缓存、状态过期和离线告警已有自动测试。

#### DATA-FRONT-02 进度、修订与分层刷新

- **功能描述：** 记录任务开始、阶段变化、有效动作、评论生成、平台提交、outbox 写入和经理机回收，并分别刷新总览、任务进度和结果。
- **输入与前置：** 执行任务包含稳定的运营任务、机器、账号、派发和远程执行标识。
- **输出结果：** 连续进度事件、当前结果、修订历史、数据新鲜度和最近同步时间。
- **业务规则：** 计数事件同时记录目标和实际；`RESULT_UNKNOWN` 不自动重发；自动刷新不得重置用户当前查看位置。
- **验收标准：** 经理机和员工机看到一致阶段；当前结果采用最高修订；刷新串行且页面失焦时降频。
- **当前进度：** `部分实现`。事件模型、修订、分层刷新和页面展示已完成；完整实时实机时序待验证。

#### UX-FRONT-01 响应式布局与页面状态

- **功能描述：** 使用顶部全局导航、单一页面滚动和按需展开详情，并保留视图、筛选、机器选择和滚动位置。
- **输入与前置：** 页面运行在桌面或窄屏浏览器中。
- **输出结果：** 适配 1440px、1024px 和单栏布局的经理机与员工机页面。
- **业务规则：** 每页只有一个一级标题；技术编号和原始 JSON 默认折叠；状态不只依赖颜色。
- **验收标准：** 页面不出现多个竞争的纵向滚动区；刷新和返回不丢失查看上下文；键盘可以访问主要控件。
- **当前进度：** `部分实现`。布局、焦点样式和主要 ARIA 标签已存在，完整键盘和读屏验收待完成。

#### UX-FRONT-02 历史列表分页

- **功能描述：** 为任务、Agent 消息、结果和审计历史提供统一分页、游标或分段加载。
- **输入与前置：** 列表接口支持稳定排序、筛选和分页参数。
- **输出结果：** 当前分段记录、总量或下一页游标。
- **业务规则：** 不一次加载无限历史；加载更多不改变筛选和已打开详情。
- **验收标准：** 万级历史记录下首屏可用，翻页无重复和遗漏。
- **当前进度：** `待实现`。结果回收已有游标，网站历史列表尚未统一分页。

| 入站事件 | `event_id/event_type` | 评论或私信事件编号和类型 | 文本 + 枚举 | 是 | 执行机采集器 | 采集到事件时 |
| 入站事件 | `natural_key` | 平台事件去重键 | 文本 | 是 | 执行机采集器 | 入库前 |
| 操作事件 | `task_id/action/status` | 任务逐项执行记录 | 结构化记录 | 是 | 执行机执行器 | 动作发生时 |
| 指标快照 | `entity_type/entity_id` | 账号或笔记实体 | 文本 | 是 | 执行机采集器 | 每次采集 |
| 指标快照 | `collected_at/metrics` | 采集时间和指标值 | 时间 + 结构化对象 | 是 | 执行机采集器 | 每次采集 |
| 报告 | `report_id/report_version` | 日报或周报及修订版本 | 文本 + 整数 | 生成报告时必填 | 经理机报告服务 | 生成报告时 |

尚未确定并保留为待填写的数据包括：发布作品 ID 和稳定链接来源、曝光/阅读/播放数据源、账号日运营成本、真实成功率样本与窗口、经理机可管理执行机上限、数据保留周期和日报/周报格式。

数据必须遵守以下规则：没采到不能写成 0；任务成功必须有页面或平台回读；`RESULT_UNKNOWN` 不自动重试；历史快照和原报告不覆盖；诊断、账号配置、数据库和 SSH 私有凭据不得提交到 GitHub。

## 六、开发规范

### 1. 版本管理规则

下面以 `PUBLISH-05 执行发布任务` 从1.0升级到1.1为例。

1. **功能编号固定。** 功能实现升级后仍叫 `PUBLISH-05`，只把版本从1.0改为1.1；只有业务目标变了，才建立新的功能编号。
2. **所有可用版本统一登记。** 版本清单分别记录 `PUBLISH-05 1.0｜正式使用` 和 `PUBLISH-05 1.1｜小范围试用`，并写清哪些经理、设备或账号可以使用1.1。
3. **实际执行方选择兼容版本。** A05下发发布任务时给出允许版本范围；真正执行任务的Agent或固定程序根据本机客户端、依赖和版本健康情况，从范围内选择1.0或1.1。
4. **一个任务只使用一个版本。** 某条发布任务开工时选定1.1后，从上传内容到返回结果都保持1.1；结果中必须写明实际版本，执行中不自动切换到1.0。
5. **新版本逐步验证。** 1.1先完成固定测试，再用历史发布任务回放，然后只在一台测试设备和少量测试账号真实试用；通过后才扩大范围。
6. **升级范围可以很小。** 1.1可以先只开放给PC050和指定测试账号，其他发布设备继续使用1.0，不要求所有机器同时升级。
7. **异常只回退后续任务。** 1.1出现问题时，后续新任务切回1.0；已经开工的1.1任务按原任务安全完成或停止，已经形成的平台作品和业务结果不删除。
8. **旧版本最后停用。** 只有1.1验收通过、计划切换范围已完成、并且没有在途任务继续使用1.0时，才能把1.0标记为停用。

一次发布任务至少要留下以下版本记录：

- 功能编号：`PUBLISH-05`
- 允许版本：`1.0至1.1`
- 实际使用版本：`1.1`
- 执行设备：`PC050`
- 执行账号：实际账号编号
- 任务编号：实际发布任务编号
- 选择原因：本机环境通过1.1兼容测试
- 最终结果：成功、失败、待确认或已停止

### 2. 功能包打包规则

下面以 `PUBLISH-05 1.1` 功能包为例。

1. **使用固定目录。** 正式目录为 `TK跟发/发布模块/PUBLISH-05/1.1/`；1.0和1.1各自保留独立目录，不能互相覆盖。
2. **一个包只改一个主要功能。** `PUBLISH-05 1.1` 只修改“执行发布任务”；如果同时修改“生成发布窗口”，应另建 `PUBLISH-02` 的新版本。
3. **包内先说明身份和入口。** `manifest.json` 必须写明功能编号、版本、适用层级、支持环境、依赖版本、运行入口和执行方式。
4. **执行方式必须明确。** `PUBLISH-05` 标记为 `固定程序执行`；需要Agent分析网络问题的 `PUBLISH-08` 可标记为 `Agent与程序配合`，不能让执行设备靠猜测决定。
5. **交付内容必须完整。** 包内必须同时提供功能说明、正式代码、配置示例、固定测试、历史回放样本、版本变化说明和回退方法。
6. **业务规则放在功能包里。** “不能串账号”“同一任务不能重复发布”等规则属于 `PUBLISH-05`；负责接收、转发和留档任务的公共程序只传递任务和结果，不替发布功能做业务判断。
7. **统一上传且只新增版本。** 开发人员通过局域网上传工具建立1.1目录，记录上传人和时间；禁止覆盖1.0，也不能把桌面或临时目录当作正式交付位置。
8. **先测试，再安装到本机运行。** 1.1通过规定测试后才能列为可用版本；获准设备把功能包装到本机，正式执行时不跨机读取开发人员或经理机器的工作目录，并回报实际安装版本。

`PUBLISH-05 1.1` 功能包至少包含：

```text
TK跟发/
└─ 发布模块/
   └─ PUBLISH-05/
      ├─ 1.0/                         旧稳定版本，继续保留
      └─ 1.1/
         ├─ manifest.json             功能身份、版本、环境、依赖、入口和执行方式
         ├─ README.md                 功能用途、输入、输出和验收标准
         ├─ runtime/                  正式执行代码
         ├─ config/                   配置示例，不写死设备和账号
         ├─ tests/                    固定测试与历史回放样本
         ├─ CHANGELOG.md              1.1相比1.0改了什么
         └─ ROLLBACK.md               出现问题时怎样切回1.0
```

`manifest.json` 至少写清：

```text
业务模块：TK跟发发布模块
功能编号：PUBLISH-05
功能名称：执行发布任务
版本：1.1
适用层级：执行层
执行方式：固定程序执行
支持环境：已通过适配性测试的目标环境
依赖：账号身份、待发内容、发布任务和客户端入口
运行入口：runtime中的正式入口
回退版本：1.0
```
