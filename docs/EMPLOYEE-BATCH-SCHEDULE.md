# 员工机定时批次

每日计划生成完整批次时间表并提前投递员工机。每个批次具有独立任务编号、计划时间、
结束时间、指标和前一批任务编号。经理机负责投递和回收，员工执行服务负责到点启动，
后续批次无需等待经理机再次在线或重新生成。

通过账号运营配置 `daily_policy.batch_start_times` 指定北京时间，例如：

```json
{"daily_policy":{"batch_start_times":["15:00","16:00","17:00"],"action_spacing_seconds":300}}
```

浏览30、点赞6会均分为三个10/2批次。每批最多15篇；未指定时间表时按原批间隔生成
计划时间。到点时若上一批仍在执行则顺延；上一批完成后仍须满足批间隔。
批间隔用于两个批次之间，每篇阅读与点赞的节奏独立。

员工执行服务每10秒读取本地队列，也接收已送达inbox但SSH唤醒确认中断的任务。
重启后从既有持久化记录继续。接受任务后60秒仍未启动、原runner已退出且无领取证据，
可以恢复原任务启动；已经领取或发生业务动作的进程退出保持结果待核对。
同账号串行，前批失败、阻塞或结果未知时停止其后续批次，其他账号独立推进。
过期批次写阻塞回执，暂停机器保持暂停。

队列查询读取最近完整落盘的状态，写入继续使用事务锁和原子替换。等待时刻的任务
保持排队，避免定时检查反复写入整个历史状态文件。

新生成计划使用 `strategy.dispatch_mode=employee_schedule`。已存在的增量计划保留原
执行方式和证据，不能把完整日指标再次下发。迁移时先核对实际数、在途任务和未知结果，
只对尚未投递的剩余额度建立时间表。每批的 `scheduled_at`、`batch_index` 与
`batch_count` 随任务回执展示在员工控制台。
